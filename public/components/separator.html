In Context — Article Layout

Separators should be used within content to divide thematic sections — not as spacers or page-level breaks.

Anti-Patterns

Don't: Separator as spacer

Never use a separator purely to add vertical space. Use CSS margin/padding or the Spaced variant only when a visible line is appropriate.

Don't: Full-width page break bands

Never use full-bleed coloured bands or thick horizontal bars to "break" the page between sections. Page sections should flow naturally using consistent padding and background colours — not hard visual fences.

5. Content Guidance

When to use

  • Use Default for general content separation within a page section (e.g., between paragraphs in an article).
  • Use Thick to delineate major thematic shifts within a single content area.
  • Use Accent sparingly as a decorative element — typically centred under headings or between testimonials.
  • Use Spaced where generous whitespace reinforces visual hierarchy and a visible line is semantically appropriate.
  • Use With Label for logical branching ("or") or named section breaks within a flow.

When NOT to use

Rule 1 — Never use separators as spacers.
If the goal is vertical whitespace between sections, use CSS padding/margin on the section container. Stacking invisible or decorative <hr> elements to "push content apart" is a misuse of the component and creates accessibility noise.
Rule 2 — Never use full-width coloured break bands between page sections.
The current site uses thick, full-bleed coloured bars (e.g., 8px dark blue bands) to visually "fence off" page sections. This creates a jarring, segmented reading experience. Instead, page sections should transition naturally using consistent padding, alternating background colours (--caat-grey / white), and clear heading hierarchy. The separator component is for within-content use only.
  • Do not stack multiple separators — one is always sufficient.
  • Do not use separators inside cards, accordions, or other contained components (use the component's own internal spacing).
  • Do not use separators between page-level sections — rely on section padding and background colours instead.

6. Semantic HTML

<!-- Default / Thick / Accent / Spaced -->
<hr class="caat-separator caat-separator--{variant}">

<!-- With Label -->
<div class="caat-separator caat-separator--with-label">
  <span class="caat-separator__label">or</span>
</div>

<!-- Decorative (aria-hidden) -->
<hr class="caat-separator" aria-hidden="true" role="presentation">

9. SEO

  • No SEO impact — separators do not contribute to heading structure or indexable content.
  • Ensure separators do not break logical heading hierarchy when placed between sections.

10. Analytics

  • No click/interaction tracking required — separators are non-interactive.
  • Component impression tracking may be applied at the page-section level if needed for layout A/B testing.

11. AEM Implementation Notes

  • Resource type: caat/components/separator
  • Sling model exposes variant (String) and labelText (String).
  • HTL renders <hr> for all variants except "With Label", which renders a <div> wrapper.
  • Author dialog uses a showhide listener to reveal the label field only when variant = "with-label".
  • Component is policy-enabled; allowed variants can be restricted per template.

14. Definition of Done

  • All 5 variants render correctly in design-system preview.
  • CSS uses only design tokens — no hard-coded colours.
  • AEM dialog created with show/hide logic for label field.
  • HTL template passes W3C validation.
  • Accessibility audit — no violations.
  • Responsive testing complete (mobile, tablet, desktop).
  • Code reviewed and merged to develop branch.
  • QA checklist signed off.
