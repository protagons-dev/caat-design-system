Colour contrast guide

Use these combinations for text, buttons, links, badges, and backgrounds. Normal text should meet at least 4.5:1 contrast; large text and meaningful non-text UI indicators should meet at least 3:1.

Dark blue + whiteApproved: primary buttons, footer, hero cards

Light green + dark greenApproved: success, low-emphasis labels

Sky blue + greenAvoid for text; low contrast and unclear state

Text and links

  • Use dark blue or ink for body text.
  • Links must be distinguishable by more than colour when embedded in paragraphs; use underline or context.
  • Avoid green links on light-blue or grey backgrounds.

Buttons

  • Primary: dark blue background with white text.
  • Secondary: use green only when contrast is verified; darken green for small text if needed.
  • Disabled: use muted styling, but do not rely on colour alone to explain why disabled.

Badges and backgrounds

  • Use light backgrounds with dark text for informational badges.
  • Reserve lime for accents, highlights, dividers, and chart marks.
  • Never place body copy over untested photography or gradients.

Typography scale

Type stack: Libre Franklin is the primary CAAT web typeface. Arial is the secondary fallback for editable, system, and email-safe contexts. Use standard letter spacing for body copy; reserve subtle negative tracking only for large headings.

  • Show result titles, content type, date or audience when relevant, and a short excerpt.
  • Use filters for high-value content types or audiences only; avoid creating empty filter combinations.

03 Component guidance

Do and don’t examples for key components

Use these quick rules when applying the design system in AEM, Account Engagement, and campaign pages.

Hero

Do
  • Use one audience-specific message.
  • Choose images with quiet space for the card.
  • Keep faces and hands out from under overlays.
Don’t
  • Cover meaningful faces, logos, or actions.
  • Use busy images behind small text.
  • Add multiple competing CTAs.

Buttons and CTAs

Do
  • Use one primary CTA per section.
  • Start CTA labels with a verb.
  • Use outlines for secondary actions.
Don’t
  • Stack several primary buttons together.
  • Use vague labels like “click here.”
  • Use colour alone to show state.

Cards

Do
  • Keep cards parallel in structure.
  • Use descriptive headings and links.
  • Use consistent image ratios in a grid.
Don’t
  • Put critical text only inside images.
  • Mix unrelated content types in one grid.
  • Make an entire dense card feel like a button without clear focus.

Footer

Do
  • Group links by task or audience.
  • Include required legal and accessibility links.
  • Keep social links labelled for assistive tech.
Don’t
  • Hide privacy or terms links in tiny low-contrast text.
  • Rename established footer links unnecessarily.
  • Remove contact pathways from campaign pages without approval.

Hero image, copy, and overlap rules

Heroes should orient visitors quickly, preserve the image’s focal point, and keep the CTA usable on mobile. Use them for page introductions, campaign landing pages, and major story moments—not for every content block.

Recommended text length

  • Eyebrow: 1–3 words.
  • Headline: 6–12 words, ideally under two lines on desktop.
  • Summary: 18–35 words.
  • CTA: 2–5 words, starting with a verb.

Image safe zones

  • Keep faces, logos, text, and key details out of the overlay zone.
  • Use centre-right crops when the content card sits left.
  • Test desktop, tablet, and mobile before publishing.

Mobile behaviour

  • Stack the card below the image or use the capped bottom overlap.
  • Reduce image height before reducing legibility.
  • Avoid placing small text inside the image itself.

Busy images or people

  • Add a subtle gradient overlay only when needed for readability.
  • Choose images with quiet negative space for the card.
  • Never cover a person’s face, logo, or meaningful action with the headline or CTA.

Strong hero usage

Headline: A retirement solution where everyone wins

Why it works: concise message, one audience need, calm visual field, clear next step, and no meaningful image detail hidden under the card.

Weak hero usage

Headline: Learn more about all of our services and programs today

Why it fails: vague promise, no audience, too many possible actions, and a busy image that competes with the message.

08 AEM implementation process

Requirements to developer handoff to pipeline workback

Use this process to turn the design-system components into authorable Adobe Experience Manager components and page templates that can replace existing CAATpension.ca pages with minimal disruption.

Operating model

The goal is to separate content, presentation, and release risk. Requirements define the authoring experience first, developer handoff translates each pattern into AEM-ready contracts, and the pipeline workback sequences build, QA, migration, and launch.

1

Requirements

Define what the component does, who authors it, where it appears, and what existing pages it will replace.

  • Inventory current CAATpension.ca templates and components.
  • Group components by reusable pattern, not by one-off page.
  • Capture fields, variants, states, responsive behaviour, and SEO requirements.
  • Flag legal, compliance, analytics, and accessibility needs early.
2

Developer handoff

Convert each approved pattern into a component contract that developers can build without guessing.

  • Provide rendered example, markup, CSS tokens, and interaction notes.
  • Define AEM dialog fields, allowed values, defaults, and validation.
  • Map image, link, date, author, category, and schema fields.
  • Document authoring instructions and fallback behaviour.
3

Build and QA

Develop proxy components, templates, client libraries, content models, and test coverage in a controlled branch.

  • Prefer extending Core Components where possible.
  • Build component variants through policies, style systems, and dialog options.
  • Test accessibility, responsive behaviour, SEO tags, schema, and analytics events.
  • Run author review before content migration begins.
4

Pipeline and rollout

Release in waves so the team can replace pages safely while preserving URLs, SEO equity, and author confidence.

  • Deploy to lower environments first, then staging, then production.
  • Use redirects only when URLs must change.
  • Track launch defects, search visibility, analytics, and author feedback.
  • Retire duplicate legacy components after migration.

Requirements intake checklist

Use one requirements brief per component or template. The brief should be short enough to complete quickly but detailed enough to prevent rework.

  • Component name and business purpose
